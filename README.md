Ниже вариант **простого рабочего процесса для команды из 4 человек**. Термины оставляю в скобках.

# Workflow разработки через GitLab

## 1. Создание задачи

Сначала создаётся задача в GitLab (**Issue**).

В задаче нужно описать:

```text
что нужно сделать;
зачем это нужно;
какой ожидается результат;
как проверить, что задача выполнена;
есть ли макеты, скриншоты, примеры, ссылки.
```

Пример:

```text
Задача: Добавить чат обратной связи в демо-версию ZTL Online.

Ожидаемый результат:
Пользователь может открыть окно чата, написать сообщение, а сотрудник разработки получает обращение с информацией о пользователе и странице, с которой отправлено сообщение.
```

На этом этапе задача находится в статусе:

```text
Новая / в очереди (Backlog)
```

---

## 2. Назначение задачи исполнителю

Задача назначается на разработчика (**Assignee**).

В вашем случае — на вас.

Дополнительно можно указать:

```text
приоритет;
тип задачи;
планируемый релиз;
срок выполнения;
ответственных за проверку.
```

Используемые элементы GitLab:

```text
Assignee — ответственный исполнитель;
Labels — метки задачи;
Milestone — релиз, этап или спринт.
```

Пример меток:

```text
type::feature
status::in-dev
priority::medium
module::feedback-chat
```

---

## 3. Перевод задачи в разработку

Когда вы начинаете работу, задача переводится в статус:

```text
В разработке (In Development)
```

В GitLab это можно сделать перемещением карточки на доске (**Issue Board**) или сменой метки (**Label**).

На этом этапе вы уточняете задачу, смотрите код, проектируете решение и определяете, какие файлы будут изменяться.

---

## 4. Создание отдельной ветки

Под задачу создаётся отдельная ветка в Git (**Branch**).

Пример:

```bash
git checkout develop
git pull
git checkout -b feature/feedback-chat
```

Ветка нужна, чтобы не менять основную версию приложения напрямую.

Рекомендуемые названия веток:

```text
feature/feedback-chat       — новая функция
bugfix/order-save-error     — исправление ошибки
hotfix/login-critical-bug   — срочное исправление
refactor/order-module       — переработка кода
```

На этом этапе код ещё не попадает ни в `develop`, ни в `master`.

---

## 5. Разработка и первичная проверка

Вы пишете код, меняете интерфейс, настраиваете окружение, добавляете миграции, правите Docker/Nginx/БД, если нужно.

После этого вы сами делаете первичную проверку:

```text
приложение запускается;
ошибок в логах нет;
основной сценарий работает;
изменение не ломает очевидные соседние функции;
код можно собрать;
тестовый стенд обновляется.
```

Это этап:

```text
Первичная проверка разработчиком (Developer Self-Test)
```

Важно: до передачи другим специалистам задача не должна быть в состоянии «я вроде написал, но сам не запускал».

---

## 6. Коммит изменений

После первичной проверки изменения фиксируются в Git (**Commit**).

Пример:

```bash
git add .
git commit -m "Add feedback chat widget"
git push origin feature/feedback-chat
```

Коммит — это сохранённый набор изменений с пояснением.

Хорошо, если сообщения коммитов понятные:

```text
Add feedback chat widget
Fix message saving error
Update feedback form validation
Add migration for feedback messages
```

---

## 7. Создание запроса на слияние

После отправки ветки в GitLab создаётся запрос на слияние (**Merge Request / MR**).

Направление:

```text
feature/feedback-chat → develop
```

Merge Request — это центральное место, где видно:

```text
какие файлы изменены;
какие строки кода изменены;
какая задача связана с изменением;
кто должен проверить;
какие проверки прошли;
какие замечания оставлены;
можно ли вливать изменения дальше.
```

---

## 8. Заполнение описания Merge Request

В MR нужно кратко описать, что сделано и как проверять.

Пример структуры:

```text
Что сделано:
- добавлено окно обратной связи;
- сохраняются сообщения пользователя;
- к сообщению добавляется текущая страница;
- добавлена таблица feedback_messages.

Как проверить:
1. Открыть демо-версию.
2. Нажать кнопку обратной связи.
3. Отправить сообщение.
4. Проверить, что сообщение появилось в админке.
5. Проверить, что указана страница, с которой отправлено обращение.

Риски:
- изменение затрагивает frontend;
- добавлена новая таблица в БД;
- нужна проверка прав доступа.
```

На этом этапе статус задачи:

```text
Готово к проверке (Ready for Review)
```

---

## 9. Автоматические проверки

После создания MR запускается автоматическая проверка (**CI/CD Pipeline**).

Pipeline — это набор автоматических шагов, которые GitLab выполняет сам.

Минимально полезные проверки:

```text
проверка стиля кода (Lint);
запуск тестов (Tests);
сборка приложения (Build);
проверка Docker-образа;
поиск случайно добавленных паролей и токенов (Secret Detection);
базовая проверка зависимостей на уязвимости (Dependency Scan).
```

Если pipeline красный — MR нельзя принимать, сначала нужно исправить ошибки.

Статус:

```text
Автоматическая проверка (Pipeline)
```

---

## 10. Передача на проверку кода

Дальше MR назначается специалисту по проверке кода (**Code Reviewer**).

Он смотрит не «работает ли кнопка», а качество реализации.

Проверяет:

```text
правильно ли выбрана архитектура;
нет ли лишнего усложнения;
нет ли дублирования кода;
нормально ли обработаны ошибки;
безопасно ли обрабатываются данные пользователя;
нет ли SQL-инъекций, XSS, утечек данных;
корректно ли сделаны миграции БД;
не сломана ли структура проекта;
понятно ли другому разработчику, что происходит.
```

Результат проверки:

```text
одобрено (Approve);
или оставлены замечания (Comments / Review Threads).
```

Если есть замечания, MR возвращается вам на доработку.

Статус:

```text
Проверка кода (Code Review)
```

---

## 11. Исправление замечаний по коду

Если code reviewer оставил замечания, вы исправляете код в той же ветке.

Пример:

```bash
git add .
git commit -m "Fix code review comments"
git push
```

MR обновится автоматически.

После этого code reviewer повторно смотрит изменения.

Цикл может повторяться:

```text
замечание → исправление → повторная проверка → одобрение
```

Статус:

```text
Требуются исправления (Changes Requested)
```

---

## 12. Передача на проверку интерфейса и процессов

Параллельно или после code review MR передаётся специалисту по визуальной части и процессам (**UI/UX and Process Reviewer**).

Он проверяет не код, а поведение приложения глазами пользователя.

Проверяет:

```text
понятно ли пользователю, что делать;
нет ли лишних шагов;
логично ли расположены кнопки и формы;
понятны ли сообщения об ошибках;
не ломается ли внешний вид;
нормально ли выглядит на разных экранах;
соответствует ли поведение бизнес-процессу;
не создаёт ли новый функционал путаницу для пользователей.
```

Результат:

```text
одобрено (Approve);
или замечания по интерфейсу / процессу.
```

Статус:

```text
Проверка интерфейса и процесса (UI/UX Review / Process Review)
```

---

## 13. Исправление замечаний по интерфейсу

Если специалист по интерфейсу нашёл проблемы, вы дорабатываете форму, текст, логику кнопок, расположение элементов, сценарии.

Пример замечаний:

```text
кнопка непонятно называется;
нет сообщения об успешной отправке;
ошибка показывается техническим текстом;
пользователь может отправить пустое сообщение;
непонятно, куда ушло обращение;
на мобильном экране окно вылезает за границы.
```

После исправления изменения снова пушатся в ту же ветку, MR обновляется.

---

## 14. Слияние в тестовую ветку

После одобрения code review и UI/process review изменения можно слить в тестовую ветку:

```text
develop
```

Это можно сделать через Merge Request:

```text
feature/feedback-chat → develop
```

`develop` — это ветка, где собирается текущая тестовая версия приложения.

После merge в `develop` желательно автоматически развернуть приложение на тестовом стенде:

```text
test.ztlonline...
```

Статус:

```text
На тестовом стенде (Deployed to Test / Staging)
```

---

## 15. Финальное тестирование

Теперь задачу проверяет тестировщик (**QA Engineer / Tester**).

Он проверяет уже не отдельный кусок кода, а готовое поведение в тестовой версии приложения.

Проверяет:

```text
основной сценарий;
альтернативные сценарии;
ошибочные действия пользователя;
права доступа;
работу с разными ролями пользователей;
проверку на пустые, длинные, некорректные данные;
регрессию — не сломалось ли что-то рядом;
работу после перезагрузки приложения;
логи приложения;
работу с БД, если нужно.
```

Пример:

```text
Пользователь отправляет сообщение из окна обратной связи.
Пользователь отправляет пустое сообщение.
Пользователь отправляет очень длинное сообщение.
Пользователь без прав пытается открыть список обращений.
Проверяется, что в БД нет мусора.
Проверяется, что в логах нет ошибок.
```

Статус:

```text
Финальное тестирование (QA Testing)
```

---

## 16. Проверка безопасности

Если изменение затрагивает авторизацию, права доступа, ввод пользовательских данных, файлы, API или интеграции — нужна отдельная проверка безопасности.

Это этап:

```text
Проверка безопасности (Security Review / Pentest)
```

Проверяется:

```text
можно ли получить чужие данные;
можно ли выполнить действие без прав;
можно ли подставить вредный HTML/JS;
можно ли сломать запросами API;
не попали ли секреты в код;
не открыты ли лишние endpoints;
не появились ли опасные настройки Docker/Nginx;
не ломается ли backup/restore, если менялась БД.
```

Для каждой мелкой задачи достаточно базовой проверки. Полноценный пентест лучше делать перед релизом.

---

## 17. Возврат на доработку после QA/security

Если тестировщик нашёл ошибку, создаётся замечание.

Можно сделать двумя способами.

### Вариант 1. Комментарий в Merge Request

Подходит для мелких исправлений:

```text
на этой форме кнопка не работает;
при пустом поле ошибка 500;
не сохраняется текст длиннее 500 символов.
```

### Вариант 2. Отдельная задача

Подходит для серьёзных ошибок:

```text
Issue: Ошибка при отправке обращения без авторизации
Issue: Пользователь видит чужие обращения
Issue: Некорректная миграция БД
```

После исправления снова проходит проверка.

Цикл:

```text
QA нашёл ошибку → разработчик исправил → QA перепроверил → одобрил
```

---

## 18. Финальное согласование

Когда все проверки пройдены, задача переходит в статус:

```text
Готово к слиянию (Ready to Merge)
```

На этом этапе должно быть:

```text
pipeline зелёный;
code review одобрен;
UI/process review одобрен;
QA одобрен;
security-проверка пройдена, если нужна;
описание MR заполнено;
нет незакрытых критичных замечаний.
```

Ответственный человек, например вы как Maintainer, принимает финальное решение.

Статус:

```text
Финальное согласование (Final Approval)
```

---

## 19. Слияние в основную ветку

После финального согласования изменения сливаются в основную ветку:

```text
develop → master
```

Или, если процесс упрощённый:

```text
feature/feedback-chat → master
```

Но я бы для вашей команды рекомендовал всё-таки:

```text
feature/* → develop → master
```

`master` или `main` — это стабильная ветка, из которой можно выпускать релиз.

Статус:

```text
Слито в основную ветку (Merged to Master/Main)
```

---

## 20. Создание релиза

После слияния в `master` можно создать релиз (**Release**) и тег (**Tag**).

Пример тега:

```text
v0.3.0
v0.3.1
v0.4.0-demo
```

В описании релиза указывается:

```text
что добавлено;
что исправлено;
какие есть ограничения;
какие миграции выполнены;
что нужно проверить после обновления;
есть ли действия администратора.
```

Статус:

```text
Релиз подготовлен (Release Created)
```

---

## 21. Деплой

После релиза выполняется выкладка приложения (**Deploy**).

Варианты:

```text
ручной деплой;
автоматический деплой через GitLab CI/CD;
деплой через Docker Compose;
деплой через Ansible;
деплой через Portainer / SSH.
```

Для вашего случая логично:

```text
merge в develop → автодеплой на test;
merge в master → ручное подтверждение деплоя на production.
```

То есть production лучше не обновлять полностью автоматически, а делать кнопку:

```text
Deploy to production
```

с ручным запуском.

---

## 22. Проверка после деплоя

После выкладки проводится короткая проверка (**Smoke Test**).

Smoke Test — это быстрая проверка, что приложение в целом живое.

Проверяется:

```text
сайт открывается;
пользователь может войти;
основная страница работает;
новая функция доступна;
критичных ошибок в логах нет;
БД доступна;
очереди/фоновые задачи работают, если есть;
интеграции не упали.
```

Статус:

```text
Проверено после деплоя (Post-deploy Check / Smoke Test)
```

# Итоговая цепочка коротко

```text
1. Задача (Issue)
2. Назначение исполнителя (Assignee)
3. Взятие в работу (In Development)
4. Создание ветки (Branch)
5. Разработка и первичная проверка (Developer Self-Test)
6. Коммит и push (Commit / Push)
7. Merge Request в develop (MR)
8. Автоматические проверки (Pipeline)
9. Проверка кода (Code Review)
10. Исправление замечаний (Changes Requested)
11. Проверка интерфейса и процесса (UI/UX Review / Process Review)
12. Исправление замечаний по интерфейсу
13. Слияние в develop (Merge to Develop)
14. Деплой на тестовый стенд (Deploy to Staging)
15. Финальное тестирование (QA Testing)
16. Проверка безопасности при необходимости (Security Review)
17. Исправление найденных ошибок
18. Финальное согласование (Final Approval)
19. Слияние в master/main (Merge to Master/Main)
20. Создание релиза (Release / Tag)
21. Деплой (Deploy)
22. Проверка после деплоя (Smoke Test)
```
